# 1장 — 세팅 · 개념 (홍섭)

> 스터디 발표용 개인 정리본. 원 노트를 구조화하고, `@` 경로 토큰 실험을 직접 돌려 확정한 버전.

## 1. Claude Code가 다루는 컨텍스트

Claude Code는 다음 5가지를 이용해 작업한다:

- 파일 시스템
- MCP (외부 도구 연결)
- 웹 접근
- 터미널
- 에디터 컨텍스트

이 컨텍스트들을 **루프(플로우)로 돌며** 문제를 처리한다.

**적용예시 (실측):** 내 클로드 환경에 MCP 서버들이 실제 연결됨 — firecrawl(웹 검색·스크랩), Atlassian(Jira/Confluence), playwright(브라우저 제어), kanban. `~/.claude/settings.json`에 `hooks`·`enabledPlugins`도 설정돼 세션 이벤트마다 개입한다.

**5종이 한 작업에서 이어져 도는 예시 — "Jira 버그 티켓 하나 고치기":**

1. **에디터 컨텍스트** — 지금 열린 파일·에러 위치를 인지
2. **MCP(Atlassian)** — Jira에서 티켓 본문·재현 절차를 가져옴
3. **파일 시스템** — Grep/Read로 관련 코드 추적
4. **웹 접근** — 쓰는 라이브러리 최신 문서 확인
5. **터미널** — 테스트 실행 → 실패 로그 보고 → 다시 3번(파일)으로

→ 5개가 한 줄로 도는 게 아니라, **터미널 결과를 보고 다시 파일로 돌아가는 순환**이 핵심. "한 번 읽고 끝"이 아니라 피드백 루프.

## 2. 체크포인트 3종

복원 단위가 3가지로 나뉜다:

| 종류 | 복원 대상 | 언제 (예시 시나리오) |
|------|-----------|----------------------|
| 대화만 | 대화 맥락만 되돌림 | 코드 결과는 맘에 드는데 **대화가 삼천포로 샜을 때** — 코드 두고 대화만 되감기 |
| code만 | 코드 변경만 되돌림 | 계획(대화)은 맞는데 **코드가 꼬였을 때** — 대화 살리고 코드만 롤백 |
| 둘다 | 대화 + 코드 함께 | **접근 자체가 틀렸을 때** — 그 시점으로 통째 복원 |

> (아직 직접 써본 적 없음 — 위는 이해용 가정 시나리오. 발표 후 실제로 `/rewind` 걸어보고 감 잡을 것.)

## 3. `@` 경로 vs 전체 경로 — 토큰 실험 (직접 측정)

**의문:** 경로 지정하면 토큰 적게 쓴다는데, 항상 `@`를 붙여야 하나? `@` 없이 전체 경로만 줘도 되나?

**실험:** 300줄(≈10,500토큰, 한글) 더미 파일 `_drafts/exp-path.md`로 두 방식 비교.

| | `@경로` | 경로만 (no `@`) |
|---|---------|------------------|
| 주입 시점 | 제출 즉시 | Claude가 Read할 때 |
| 읽는 범위 | **파일 전체** | 필요한 부분만 (offset/limit) |
| 도구 호출 | 0회 | 1회 (왕복) |
| 이번 실측 토큰 | ~10,500 (전체) | **~175** (150줄부터 5줄만) |

**결론:**

- **`@` 꼭 안 붙여도 된다.** 경로만 줘도 Claude가 Read 도구로 읽는다 (이 정리본 만드는 내내 그렇게 함).
- `@` = 편의 기능. 파일을 **통째로 즉시** 프롬프트에 첨부. 작은 파일엔 왕복 없이 편하고 싸다. **큰 파일엔 오히려 토큰 폭증.**
- 경로만 주면 Claude가 **필요한 부분만** 읽어 큰 파일에서 토큰 절약. 대신 도구 호출 1회 추가.
- 원 노트의 "경로 지정 = 토큰 절약"은 정확히는 **본문 통째 붙여넣기 대비** 절약. `@` vs 경로는 그 안에서 trade-off가 갈린다.

**한 줄 팁:** 작은 파일은 `@`로 바로, **큰 파일은 `@` 빼고 경로만** 줘서 부분 읽기 유도.

## 4. (곁가지) 드래그&드롭과 `@`

orca 등에서 드래그&드롭으로 경로 붙여넣을 때 매번 `@` 붙이는 게 번거로웠음 → 이게 3번 실험의 계기. 결론적으로 **큰 파일이면 `@` 없는 게 오히려 이득**이라 불편이 아니라 기본값으로 봐도 됨.
