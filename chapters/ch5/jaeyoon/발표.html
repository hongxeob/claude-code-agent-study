에이전트가 나에게 말하는 방식과 내가 에이전트를 읽는 방식

이 장의 한 문장

에이전트에는 출력 표면이 둘 있다. 무엇을 말하는가(출력 스타일)와 지금 어떤 상태인가(상태 표시줄). 5장은 그 둘을 모두 설정 파일로 사용자가 소유한다는 이야기다.

3장 스킬이 지식의 비용을, 4장 서브에이전트가 작업의 비용을 다뤘다면, 5장은 그 결과가 사람에게 도달하는 마지막 구간이다. 두 절이 한 장에 묶인 이유가 여기 있다 — 둘 다 "출력"이고, 둘 다 설정 파일에 소유권이 있다. 방향만 반대다.

05.2

PART 1 · 출력 스타일

형식이 아니라 시스템 프롬프트를 바꾼다

출력 스타일은 클로드 코드가 응답을 생성할 때 따르는 가이드라인의 집합이다. 핵심은 이것이 시스템 프롬프트를 직접 수정한다는 점 — 말투를 바꾸는 옵션이 아니라 응답의 근본적인 특성을 바꾸는 스위치다.

⚠ 가장 조심할 문장

default가 아닌 custom을 선택하면 "소프트웨어 엔지니어링 관련 지침이 제거된다". 코딩 지침을 남기려면 프론트매터에 keep-coding-instructions: true.

단, 이 "제거"가 내장 4종에도 걸리는지 직접 만든 스타일에만인지는 원문만으로 갈리지 않는다. 바이너리에서 필드 존재까지는 확인했지만 적용 범위는 못 찾았다 — 미확정으로 남긴다.

PART 1 · 경계

대체냐, 추가냐

원문이 던지는 가장 실용적인 구분. 둘 다 "응답 방식"을 바꾸지만, 시스템 프롬프트에 대해 하는 일이 정반대다.

♻  REPLACE

Output Style

시스템 프롬프트를 완전 대체
  • 효과기본 지침을 걷어낸다. 코딩 지침도 함께 날아갈 수 있다
  • 위험높다 — 범위가 넓고, 무엇이 사라졌는지 눈에 안 보인다
  • 적합"기본값을 쓰지 않겠다"가 목적일 때
＋  APPEND

CLAUDE.md

시스템 프롬프트에 추가
  • 효과기본 지침 위에 규칙을 얹는다
  • 위험낮다 — 빼는 게 아니라 더하는 것
  • 적합"기본값에 우리 규칙을 더하겠다"가 목적일 때
⚠ 그래서 이번 장에서 커스텀 스타일을 만들지 않았다

1 · 목적이 이미 겹친다. 교재 예시 korean-architecture-focused가 하려는 일(한국어 응답·문서화 규칙)을 이 레포에서는 CLAUDE.md가 이미 하고 있다. 두 축을 겹쳐 쓰면 어느 쪽이 이겼는지 알 수 없다.

2 · 프로젝트 수준은 혼자 만들 파일이 아니다. .claude/output-styles/에 파일을 두는 건 팀 전체의 시스템 프롬프트를 대체하는 변경이다. 이 레포의 CLAUDE.md는 "공통 스킬은 모임 논의로 선정된 것만 승격한다"고 못박고 있고, 출력 스타일은 스킬보다 영향 범위가 크다. 모임 안건이지 개인 커밋이 아니다.

3 · 도입한다면. 개인 실험은 ~/.claude/output-styles/. 팀에 넣는다면 CLAUDE.md가 못 하는 일 — 즉 "추가"가 아니라 "대체"가 필요할 때여야 한다. 발표 리허설처럼 코딩 지침 자체를 걷어내고 싶은 경우라면, 오히려 keep-coding-instructions를 켜지 않는 게 목적에 맞는다.

PART 2 · 상태 표시줄

이 장에서 유일하게 실물이 있는 기능

/statusline에 자연어로 원하는 걸 적으면 명령이 만들어진다. 내가 예전에 넣은 프롬프트의 결과물이 지금도 ~/.claude/settings.json에 살아 있다. 이번 정리를 하면서 처음 열어봤다.

/statusline 모델 정보 | 버전 정보 | 비용 정보 (현재 사용한 컨택스트 / 총 컨택스트) | 깃 상태 | 현재 위치한 브랜치

그리고 좌측에는 간단한 이모지나 아이콘 표시되도록. 색깔은 니가 생각했을 때 적절한 형태로

깃 상태 표시 시, ~는 Mod ?는 New + - 는 기호 그대로

색상은 인텔리제이 IDE 기준 Dracula 테마 색상으로

그 결과 — 실제로 화면에 뜨는 줄

~/.claude/settings.json → statusLine

🤖 Opus 5 (1M context)|🏷️ v2.1.258|📊 41.2k/1M|⚠️ Mod 3 New 1 +42 -7|🌿 feat/jyshin-chap05
위: 깨끗할 때 / 아래: 변경이 있을 때  —  색은 settings.json의 실제 ANSI 값. 이 페이지 전체 팔레트도 같은 값이다.

해부 ① 저장 형태 — 스크립트 파일이 아니다

{ "statusLine": { "type": "command", "command": "<bash 원라이너 전체>" } }

교재는 "Bash·Python·Node.js 스크립트로도 작성 가능"이라고 안내한다. 그런데 내 것은 그 선택지를 쓰지 않고 settings.json에 통째로 박아 넣은 형태다. ~/.claude/에 .sh 파일은 하나도 없다.

해부 ② 입력은 stdin JSON

해부 ③ 헬퍼 함수가 진짜로 있었다

✓ 원문 마지막 줄의 실물
  • 원문: "너무 복잡해지면 헬퍼 함수 정의하여 코드 정리하자."
  • 실물: fmt_tokens() — awk로 1,000 이상은 k, 1,000,000 이상은 M으로 축약. 정수면 1M, 아니면 1.2M.
  • 즉 노트에 적어둔 조언이 내 설정 안에 이미 구현되어 있었다.

01

출력 표면이 둘이다

무엇을 말하는가(출력 스타일)와 지금 어떤 상태인가(상태 표시줄). 둘 다 설정 파일에 소유권이 있고, 방향만 반대다.

02

대체와 추가를 구분하라

Output Style은 대체, CLAUDE.md는 추가. 같은 목적이면 위험이 낮은 쪽을 쓴다. 그래서 이번엔 커스텀 스타일을 만들지 않았다.

03

같은 지침도 어디 넣느냐가 다르다

환각 방지 지침을 스킬에 넣으면 그 작업에만, 출력 스타일에 넣으면 모든 응답에 걸린다. 4항목 중 팀 표준(4번)만 스타일이 어울린다.

04

내 설정은 다시 열어봐야 안다

fmt_tokens 헬퍼가 이미 있었고, 기호 매핑 요청은 카운트로 바뀌어 있었다. 매일 보던 한 줄인데도 열어보고서야 알았다.

발표에서 "모른다"고 말할 것

SWE 지침 제거 범위

내장 4종에도 걸리는지, 직접 만든 스타일에만인지. 원문·실측 모두로 판정 불가.

Default·Proactive 설명

바이너리에서 문자열을 못 찾았다. 없다는 근거는 아니다.

/output-styles 동작

문자열은 있으나 실행해보지 않았다.

statusLineHealthLatches

실패·지연 처리 장치로 추정될 뿐 확인하지 않았다.
