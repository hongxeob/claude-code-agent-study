# Chapter 5. 출력 인터페이스

> 상태: **확정본** — 역질문 7개 판단 반영 완료
> 실측 기준일: 2026-09-02
> 실측 환경: `claude --version` = **2.1.258**, 이 세션이 실제로 실행 중인 바이너리는 **2.1.257** (`CLAUDE_CODE_EXECPATH=~/.local/share/claude/versions/2.1.257`)

## 중심 메시지

> **에이전트에는 출력 표면이 둘 있다. 무엇을 말하는가(출력 스타일)와 지금 어떤 상태인가(상태 표시줄). 5장은 그 둘을 모두 설정 파일로 사용자가 소유한다는 이야기다.**

3장 스킬이 **지식**의 비용을, 4장 서브에이전트가 **작업**의 비용을 다뤘다면, 5장은 그 결과가 **사람에게 도달하는 마지막 구간**을 다룬다.

두 절이 한 장에 묶인 이유가 여기 있다.

- **출력 스타일** — 에이전트가 나에게 말하는 방식. 시스템 프롬프트를 **대체**해서 바꾼다.
- **상태 표시줄** — 내가 에이전트의 상태를 읽는 방식. stdin JSON을 받아 **내 스크립트**로 렌더링한다.

둘 다 "출력"이고, 둘 다 **설정 파일에 소유권이 있다**. 방향만 반대다.

## 1. 출력 스타일 커스터마이징

### 1.1 정의

**출력 스타일(output style)** : 클로드 코드가 응답을 생성할 때 따르는 가이드라인의 집합.

- 클로드 코드의 **시스템 프롬프트를 직접 수정**한다. 단순히 출력 형식을 바꾸는 게 아니라, 응답의 **근본적인 특성**을 변화시킨다.
- default가 아닌 custom을 선택하면 **"소프트웨어 엔지니어링 관련 지침이 제거됨"**.[^1]
  - 단, `keep-coding-instructions: true`를 지정하면 코딩 관련 기본 지침을 유지한 채로 커스텀 지침을 추가할 수 있다.

[^1]: **(확인 필요)** 이 "제거"가 **직접 만든 커스텀 스타일에만** 적용되는지, Default를 제외한 **내장 4종에도** 적용되는지는 원문 노트만으로 갈리지 않는다. v2.1.258 바이너리에서 `keep-coding-instructions`가 **프론트매터 키로 인식된다는 것까지는 확인**했지만, 제거의 적용 범위를 보여주는 문자열은 찾지 못했다. 실행 검증(실제로 스타일을 전환해 시스템 프롬프트 변화를 관찰)은 하지 않았다 — 전역 설정을 바꿔야 하고, 이 장의 학습 목적에 비해 부작용이 크다. **원문 서술을 그대로 두고 미확정으로 남긴다.**

**내 클로드 시스템에서 확인한 예시 (실측)**

- `keep-coding-instructions` 문자열이 **v2.1.258 바이너리 안에 존재**한다 (`strings` 기준 5회). 교재의 이 필드는 현재 버전에서도 실재한다.
- 반면 내 시스템에는 **커스텀 출력 스타일이 0개**다. `~/.claude/output-styles/`도 `.claude/output-styles/`도 **디렉터리 자체가 없다.**

### 1.2 내장 출력 스타일

`/config` → Output Style 선택.

| 스타일 | 원문 설명 |
| --- | --- |
| **Default** | 코딩 작업을 효율적으로 수행하며 간결한 답변을 제공합니다. |
| **Proactive** | 즉시 실행하고, 중단을 최소화하며, 계획보다는 행동을 선호합니다. |
| **Concise** | 서두나 부연 설명 없이 결과부터 언급하며 간결하게 답변합니다. |
| **Explanatory** | 구현 방식의 선택 이유와 코드베이스 패턴을 설명합니다. |
| **Learning** | 잠시 멈추고 실습을 위해 간단한 코드를 작성해 보라고 요청합니다. |

**내 클로드 시스템에서 확인한 예시 (실측)**

- v2.1.258 바이너리에서 **5개 이름이 모두 확인**된다. `"Default"`, 그리고 `source:` 필드와 함께 등록된 `"Proactive"`, `"Concise"`, `"Explanatory"`, `"Learning"`.
- 설명 문장 3개는 **원문 영문이 그대로** 나오고, 교재의 한국어 설명과 일치한다.

  | 스타일 | 바이너리에서 실측한 원문 |
  | --- | --- |
  | Explanatory | `Claude explains its implementation choices and codebase patterns` |
  | Concise | `Claude responds tersely, leading with results and skipping preamble and narration` |
  | Learning | `Claude pauses and asks you to write small pieces of code for hands-on practice` |

  (Default·Proactive의 설명 문자열은 이번 탐색에서 **미확인**. 없다는 뜻이 아니라 못 찾은 것이다.)
- 교재는 `/config` 경유를 안내하지만, 바이너리에는 **`/output-styles` 슬래시 명령 문자열도 존재**한다 (복수형). 직접 실행해 검증하지는 않았다.
- **교재에 없는 축 — 플러그인도 출력 스타일을 제공할 수 있다.** 플러그인 매니페스트가 인식하는 키 목록에 `agents`, `skills`, `themes`, `workflows`, `monitors`와 나란히 **`outputStyles`**가 들어 있고, `output styles from plugin`이라는 문자열도 있다. 4장에서 본 "플러그인이 서브에이전트를 배포한다"와 같은 구조가 출력 스타일에도 있는 셈이다.

### 1.3 출력 스타일 변경 방법

- 프로젝트 수준 로컬 설정 파일 : `.claude/settings.local.json`
- 팀 전체 표준 설정 파일 : `.claude/settings.json`

```json
{
    "outputStyle": "explanatory"
}
```

**내 클로드 시스템에서 확인한 예시 (실측)**

- `~/.claude/settings.json`의 최상위 키는 `effortLevel`, `enabledPlugins`, `extraKnownMarketplaces`, `hooks`, `model`, `skipDangerousModePermissionPrompt`, `statusLine`, `theme`, `tui` — **`outputStyle` 키가 없다.** 즉 **Default로 돌고 있다.**
- 이 스터디 레포에는 `.claude/settings.json`도 `.claude/settings.local.json`도 **없다.** `.claude/` 아래에는 `skills/` 하나뿐이다.
- 정리하면 **사용자 수준·프로젝트 수준 어느 쪽에서도 출력 스타일을 쓰고 있지 않다.**

### 1.4 커스텀 출력 스타일 생성

- 사용자 수준 : `~/.claude/output-styles/`
- 프로젝트 수준 : `.claude/output-styles/`

예시:

```yaml
---
name: korean-architecture-focused
description: 한국어로 응답하며 아키텍처 결정에 집중하는 스타일
keep-coding-instructions: true
---

# 커스텀 지침

## 응답 언어
항상 한국어로 응답합니다.
기술 용어는 필요에 따라 영어 원문을 사용하되
한국어 설명을 함께 제공합니다.

## 집중 영역
- 아키텍처 결정과 트레이드오프 설명
- 상세한 코드 주석 제공
- 디자인 패턴과 적용 방법 논의

## 코드 예제
코드 예제를 제공할 때:
- 한국어로 된 포괄적인 인라인 주석 포함
- 구현 선택의 이유 설명
- 잠재적인 대안과 트레이드오프 강조
```

구조는 **YAML 프론트매터 + 마크다운 본문**이다. 3장 스킬·4장 서브에이전트와 같은 형식이다. 클로드 코드의 확장 축은 전부 이 한 가지 파일 모양을 쓴다.

**내 클로드 시스템에서 확인한 예시 (실측)**

- **아직 없음.** 커스텀 출력 스타일 파일이 사용자·프로젝트 양쪽 모두 0개다.

**이번 장에서는 만들지 않기로 했다.** 이유가 곧 이 장의 요점이다.

1. **교재 예시(`korean-architecture-focused`)가 하려는 일을 이 레포에서는 이미 `CLAUDE.md`가 하고 있다.** `CLAUDE.md`의 "문서·주석·커밋 설명은 한국어" 규칙이 정확히 그것이다. 같은 목적에 두 축을 겹쳐 쓰면 어느 쪽이 이겼는지 알 수 없게 된다.
2. **프로젝트 수준 출력 스타일은 개인이 만들 수 없다.** `.claude/output-styles/`에 파일을 두면 그건 팀 전체의 **시스템 프롬프트를 대체**하는 변경이다. 이 레포의 `CLAUDE.md`는 "공통 스킬은 모임 논의로 선정된 것만 승격한다"고 못박고 있고, 출력 스타일은 스킬보다 영향 범위가 크다. **모임에서 합의할 안건이지 혼자 커밋할 파일이 아니다.**
3. **도입한다면 어디에**: 개인 실험이라면 `~/.claude/output-styles/`(내 환경 한정). 팀에 넣는다면 `CLAUDE.md`가 못 하는 일 — 즉 **"추가"가 아니라 "대체"가 필요한 경우**여야 한다. 예를 들어 스터디 발표 리허설처럼 코딩 지침 자체를 걷어내고 설명에만 집중시키고 싶을 때. 그때는 `keep-coding-instructions`를 켜지 **않는** 것이 오히려 목적에 맞는다.

### 1.5 관련 기능과의 비교

원문의 2×2 구분은 이렇다.

**응답 방식을 바꾸는 축**

| 기능 | 시스템 프롬프트에 대해 |
| --- | --- |
| Output Style | **완전 대체** |
| CLAUDE.md | **추가** |

**작업 실행을 바꾸는 축**

| 기능 | 하는 일 |
| --- | --- |
| 서브에이전트 | 독립 컨텍스트로 작업 위임 |
| 슬래시 명령어 | 저장된 프롬프트 실행 |

#### 확장 — 스킬까지 포함한 5자 비교 *(원문에 없음, 3·4장 연결용)*

3장·4장을 지나왔으므로 다섯 개를 한 표에 놓으면 경계가 선명해진다.

| 기능 | 바꾸는 것 | 컨텍스트 | 언제 들어오나 |
| --- | --- | --- | --- |
| **Output Style** | 시스템 프롬프트를 **대체** | 메인 | 세션 시작부터 계속 |
| **CLAUDE.md** | 시스템 프롬프트에 **추가** | 메인 | 세션 시작부터 계속 |
| **스킬** | **지식**을 주입 | 메인 (컨텍스트에 로드됨) | 필요할 때 (점진적 공개) |
| **서브에이전트** | **작업**을 위임 | **격리** (결과만 회수) | 호출할 때 |
| **슬래시 명령어** | 저장된 **프롬프트**를 실행 | 메인 | 사용자가 칠 때 |

- 위 둘(Output Style·CLAUDE.md)은 **항상 켜져 있는 배경**이고, 아래 셋은 **불러야 오는 것**이다.
- 서브에이전트만 컨텍스트가 격리된다 — 4장의 핵심이 이 표에서 유일한 예외로 드러난다.

### 1.6 팀 표준 출력 스타일 구축

1. **팀의 코딩 컨벤션과 문서화 표준을 스타일에 반영** — 코드 주석의 언어, 변수 명명 규칙 설명 방식, 아키텍처 결정 문서화 수준 등을 명시.
2. **응답의 상세 수준 정의** — 간결한 응답 vs 상세한 설명.
3. **보안 관련 지침 포함.**

**내 클로드 시스템에서 확인한 예시 (실측)**

- 1번에 해당하는 내용(한국어 문서·개인 폴더 격리·공통 스킬 승격 절차)은 이 레포에서 **`CLAUDE.md`에 들어 있다.** 출력 스타일로 옮긴 적은 없다.
- 팀 공유용 `.claude/settings.json`이 아예 없으므로, **현재 구조로는 팀 표준 출력 스타일을 배포할 통로 자체가 없다.** 도입하려면 그 파일을 만드는 것이 첫 단계다.

### 1.7 출력 스타일에서 환각 방지 지침

환각을 줄이는 지침을 **시스템 수준에서 적용**할 수 있다.

1. URL 및 출처 검증 지침
2. 불확실성 표현 허용
3. 도구 결과 기반 응답 강제
4. 팀 환경에서의 환각 방지 표준

> 원문 노트에는 **네 항목의 제목만** 있고 각각의 내용이 없다. 없는 내용을 채우면 그 자체가 환각이므로 **제목만 그대로 둔다.** 대신 아래에 내 시스템에서 대응되는 실물만 붙인다.

**내 클로드 시스템에서 확인한 예시 (실측)**

- **출력 스타일로는 아직 없음.** 대신 같은 목적의 지침이 **스킬 안에** 들어 있다. 지금 이 정리본을 만드는 `.claude/skills/pre-chapter-prep/SKILL.md`의 규칙이 그 예다.
  - *"적용예시는 파일을 읽고 확인된 것만. 기억으로 쓰지 마라. 없으면 아직 없음으로."* → **3번(도구 결과 기반 응답 강제)**
  - *"원문에 없는 사실 지어내기 금지. 빈틈은 `(확인 필요)` + 역질문."* → **2번(불확실성 표현 허용)**
- **여기서 얻은 관찰**: 같은 지침을 스킬에 넣으면 **그 작업을 할 때만** 걸리고, 출력 스타일에 넣으면 **모든 응답에** 걸린다. 4항목 중 4번(팀 환경 표준)만 출력 스타일이 어울리고, 1~3번은 스킬로도 충분하다.

## 2. 상태 표시줄

`/statusline`을 활용해 커스터마이징할 수 있다.

원문에 남긴 프롬프트:

```
/statusline 모델 정보 | 버전 정보 | 비용 정보 (현재 사용한 컨택스트 / 총 컨택스트) | 깃 상태 | 현재 위치한 브랜치

그리고 좌측에는 간단한 이모지나 아이콘 표시되도록. 색깔은 니가 생각했을 때 적절한 형태로

깃 상태 표시 시, ~는 Mod ?는 New + - 는 기호 그대로

색상은 인텔리제이 IDE 기준 Dracula 테마 색상으로
```

- 상태 표시줄은 **스크립트로도 작성 가능**하다. Bash, Python, Node.js 등.
- **너무 복잡해지면 헬퍼 함수를 정의해 코드를 정리하자.**

### 2.1 실측 — 그 프롬프트의 결과물 해부

**이 장에서 유일하게 내 시스템에 실물이 있는 기능이다.** 위 프롬프트로 만든 것이 `~/.claude/settings.json`에 그대로 살아 있다.

**저장 형태**

- 스크립트 파일이 아니라 **인라인 명령 문자열**이다.
  ```json
  { "statusLine": { "type": "command", "command": "<bash 원라이너>" } }
  ```
- `~/.claude/`에 `.sh` 파일은 하나도 없다. 교재가 "스크립트로도 작성 가능"이라고 한 그 선택지를 **쓰지 않고** settings.json에 통째로 박아 넣은 형태다.

**입력은 stdin JSON**

`input=$(cat)`으로 받아 `jq`로 뽑는 필드가 5개다.

| jq 경로 | 쓰임 |
| --- | --- |
| `.model.display_name` | 모델 이름 |
| `.version` | 클로드 코드 버전 |
| `.context_window.total_input_tokens` | 사용한 컨텍스트 |
| `.context_window.context_window_size` | 총 컨텍스트 |
| `.workspace.current_dir` | git 조회 기준 디렉터리 |

**헬퍼 함수가 실제로 있다**

`fmt_tokens()` — awk로 1,000 이상은 `k`, 1,000,000 이상은 `M`으로 축약한다. 정수면 `1M`, 아니면 `1.2M`. 원문 마지막 줄 *"너무 복잡해지면 헬퍼 함수 정의하여 코드 정리하자"*의 실물이 이것이다.

**git 상태 처리**

- `git --no-optional-locks`로 인덱스 락을 피한다 — 상태 표시줄은 매 턴 돌기 때문에 락 충돌을 막아야 한다.
- `status --porcelain`으로 tracked / untracked 개수를 세고, `diff --shortstat HEAD`에서 insertion / deletion을 뽑는다.
- 깨끗하면 `✅ clean`, 아니면 `⚠️` + 변경 요약.

**색상은 두 방식이 섞여 있다**

| 구분 | 방식 | 값 |
| --- | --- | --- |
| 모델 / 버전 / 컨텍스트 / 브랜치 | ANSI 256색 | `208` 주황 · `75` 파랑 · `245` 회색 · `176` 보라 |
| 추가 / 수정 / 삭제·미추적 | 24비트 트루컬러 | `195,232,135` · `128,203,196` · `247,118,105` |

변수명이 `IJ_ADDED`, `IJ_MODIFIED`, `IJ_DELETED`, `IJ_UNKNOWN`이다. **`IJ` = IntelliJ** — 프롬프트의 "인텔리제이 IDE 기준"이 변수명에까지 남았다.

**최종 출력 형태**

```
🤖 모델  |  🏷️ v버전  |  📊 사용/전체  |  ✅ clean  |  🌿 브랜치
🤖 모델  |  🏷️ v버전  |  📊 사용/전체  |  ⚠️ Mod 3 New 1 +42 -7  |  🌿 브랜치
```

### 2.2 프롬프트와 결과가 어긋난 지점

프롬프트는 **`~`는 Mod, `?`는 New** 라고 `git status` 기호를 라벨로 바꿔달라고 요청했다. 그런데 생성된 스크립트는 **`Mod 3` `New 1`처럼 라벨 + 개수**로 구현했다. `+`/`-`만 요청대로 기호를 유지했다.

**이건 요청과 다르다.** 다만 결과적으로는 상태 표시줄이라는 좁은 한 줄에 더 어울린다 — 파일 목록이 아니라 요약을 보여주는 자리이기 때문이다.

**여기서 얻은 관찰**: 상태 표시줄처럼 **한 번 만들고 계속 쓰는** 산출물은, 프롬프트대로 나왔는지 나중에 다시 열어보기 전까지 모른다. 이 정리본을 쓰면서 `settings.json`을 실제로 읽어보고서야 알았다.

### 2.3 그 밖에

- 바이너리에 `statusLine`이 32회, 내부 식별자 `statusLineHealthLatches`가 존재한다. 상태 표시줄 명령이 실패·지연될 때를 다루는 장치로 보이지만 **동작은 확인하지 않았다.**
