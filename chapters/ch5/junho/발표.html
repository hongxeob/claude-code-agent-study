핵심 개념 1/4

커스텀 스타일은 추가가 아니라 대체다

커스텀 출력 스타일은 keep-coding-instructions: true를 켜지 않는 한, 내장된 소프트웨어 엔지니어링 지시문을 빼버린다.

사라지는 것

  • 변경 범위를 어떻게 잡을지
  • 주석을 어떻게 쓸지
  • 작업을 어떻게 검증할지

나타나는 증상

  • 변경을 반쯤 하다 만다
  • 검증을 건너뛴다
  • 엉뚱한 곳에 주석을 단다
  • 경고가 뜨지 않는다

모델 문제가 아니라 스타일이 지시문을 지운 것이다. 페르소나 스타일을 하나 만든 직후 코딩 품질이 떨어졌다면 이걸 의심한다.

keep-coding-instructions: true   # 이 한 줄로 방지

핵심 개념 2/4

조립은 1회, 전송은 매 턴

LLM API는 stateless다. 모델은 이전 대화를 기억하지 못하고, 매 요청을 처음 보듯 받는다.

전송 — 매 턴

1턴: [시스템] + [유저1]
2턴: [시스템] + [유저1][응답1] + [유저2]
3턴: [시스템] + [유저1][응답1]
              + [유저2][응답2] + [유저3]
      ^^^^^^^^
      매번 똑같이 맨 앞에

조립 — 1회

세션 시작
  └ 파일 읽기 → 문자열 조립   ← 1회
      ├ 1턴: [조립된 문자열] 전송
      ├ 2턴: [조립된 문자열] 전송
      └ 3턴: [조립된 문자열] 전송
세션 중간에 outputStyle을 바꿔도 안 먹히는 이유 — 전송이 안 돼서가 아니라 이미 만들어진 문자열이 계속 쓰이기 때문. 그래서 /clear가 필요하다.
"저장은 했는데 안 바뀐다"의 대부분이 이것.

핵심 개념 3/4

메인 에이전트 루프에만 적용된다

서브에이전트는 자기 시스템 프롬프트로 돌기 때문에 출력 스타일의 영향을 받지 않는다. 예외는 fork — 부모의 전체 시스템 프롬프트를 그대로 상속하기 때문.

실행 주체출력 스타일 적용
메인 세션적용
Subagent미적용 — 자체 시스템 프롬프트
Fork적용 — 부모 시스템 프롬프트 상속
실무 함의. "코드리뷰는 무조건 표 형식으로" 스타일을 만들어도, 리뷰를 서브에이전트에 위임하는 순간 포맷이 깨진다.

핵심 개념 4/4

매 턴 다시 보내면 매 턴 다시 과금되나

입력

시스템 프롬프트에 지시가 늘어나니 토큰도 는다. 다만 시스템 프롬프트는 내용이 동일하고 위치가 맨 앞이라 캐시가 가장 잘 걸리는 조건이다.

첫 요청에서 cache write, 이후로는 cache read. 문서도 세션 첫 요청 이후에는 프롬프트 캐싱이 비용을 줄여준다고 적고 있다.

출력

Explanatory · Learning은 설계상 Default보다 긴 응답을 만든다. Concise는 반대.

원격 · 저대역폭 환경에서는 이게 취향이 아니라 대기시간 문제가 된다.

맨 앞에 있다는 것의 양면. 캐시가 잘 걸리는 자리이면서, 동시에 바꾸면 그 뒤 전부가 무효화되는 자리이기도 하다. 모델을 바꿀 때 캐시 경고가 뜨는 이유가 같다.

내장 스타일 5종

스타일동작쓸 때
Default기존 엔지니어링 시스템 프롬프트기본
Proactive즉시 실행. 사소한 결정은 멈춰 묻는 대신 가정하고, 계획보다 행동을 선호. permission mode는 건드리지 않는다 — 무엇이 승인 없이 실행되는지는 여전히 permission mode가 결정반복적 · 저위험 작업
Concise결론부터, 서론과 중계 설명 생략. 단 엔지니어링 작업 자체는 Default만큼 철저하고, 에러 · 보안 경고 · 파괴적 작업 확인은 항상 전문 유지 (v2.1.237+)숙련자 일상 개발
Explanatory작업 중간에 교육적 Insights를 삽입해 구현 선택과 코드베이스 패턴을 이해시킴온보딩, 낯선 레포
LearningInsights 공유에 더해 작고 전략적인 코드 조각을 직접 짜라고 요구. 코드에 TODO(human) 마커를 남김학습, 스터디
우리 스터디에 바로 쓸 수 있는 것 — Learning 모드의 TODO(human). 담당 파트를 마커로 남기게 하고 다음 주에 채워오는 방식으로 돌릴 수 있다.

4막 · 계층은 왜 대체 불가능한가

시스템 프롬프트 vs CLAUDE.md

먼저 오해 하나. "CLAUDE.md는 대화가 길어지면 뒤로 밀려서 희석된다" — 틀렸다. 시스템 프롬프트가 0번, CLAUDE.md가 1번. 둘 다 맨 앞이고, 생성 지점으로부터의 거리는 똑같이 멀어진다. 위치로는 둘을 구분할 수 없다.

차이를 만드는 건 위치가 아니라 역할 라벨이다. 시스템 프롬프트는 system이라는 별도 필드로, 메시지 배열 안에 있지도 않다.

역할모델이 받아들이는 방식
system운영자가 정한, 협상 불가능한 설정
user사용자의 요청 — 밀어낼 수도, 우선순위를 낮출 수도 있는 대상

※ 이 항목은 공식문서 서술이 아니라 LLM API 구조상의 일반론이다.

컴팩션에서는 CLAUDE.md가 오히려 강하다

직관과 반대인 사실. 루트 CLAUDE.md는 새 윈도우로 다시 읽혀 들어와 그대로 복구된다.

대상컴팩션 이후
루트 CLAUDE.md생존 재주입됨
스코프 룰 (paths: 프론트매터)소실 뭔가가 다시 트리거해야 돌아옴 — 다음 행동이 스코프에 안 맞으면 방금까지 따르던 규칙 없이 움직인다
대화 중에 타이핑한 지시소실 요약이 남긴 만큼만
hook · 도구 출력으로 주입된 컨텍스트소실 원문은 사라지고 패러프레이즈만
Skill 본문재주입되나 크면 잘림 — 앞부분을 남기므로 중요한 지시는 위쪽에
규칙을 수명으로 분류하라. 세션 전체에 걸쳐야 하는 것은 루트 CLAUDE.md로. 스코프 룰은 에이전트가 다시 발견해도 되는 파일별 디테일용이지 불변식용이 아니다.
검증법 — /compact를 수동으로 돌리고 신경 쓰는 규칙을 아직 지키는지 본다.

잘 만든 스타일의 조건 두 가지

1. 규칙이 기계적이다

"포인트당 한 줄", "em dash 금지", "caveat는 최대 하나, 마지막 줄에" — 검증할 수 있다.

"간결하게" 는 검증할 수 없다.

2. 정직성을 예외 처리한다

간결함은 단어 수의 문제이므로, 실패 · 건너뛴 단계 · 검증 안 된 수치는 여전히 말하게 한다.

이 조항이 없으면 terse 스타일은 군더더기와 함께 caveat까지 버린다.

세어볼 수 있는 규칙으로 쓰고,
줄이면 안 되는 것을 명시적으로 남긴다.

톤만 살짝 바꾸고 싶은 거라면 CLAUDE.md가 리스크가 낮은 선택이다. 내장 코딩 프롬프트를 절대 밀어내지 않으니까. 스타일 규칙은 CLAUDE.md에서도 동작한다.

  1. 우리 레포에 커밋할 프로젝트 출력 스타일을 하나 만든다면, 어떤 규칙을 넣을까? — 기계적으로 검증 가능한 형태로
  2. keep-coding-instructions: false가 기본값인 게 합리적인가?
  3. CI에 붙일 때 --bare + --json-schema 조합을 우리 파이프라인 어디에 쓸 수 있을까?
  4. 출력 스타일이 -p 모드에서도 먹는가? 문서에 명시 없음
  5. 우리 프로젝트 규칙 중 컴팩션을 넘어 살아남아야 하는 건 뭐고, 지금 어디에 들어 있나?

정리

한 문장으로

CLAUDE.md는 "이것도 알아둬",
출력 스타일은 "너는 이런 존재야".

그래서 하나는 덧붙이기만 할 수 있고, 다른 하나는 기존 지시문을 들어낼 수 있다. 계층을 알면 어느 쪽에 무엇을 넣을지가 정해진다.

부록 — Structured output과의 차이 · claude -p와 harness · Status line 원리 · 단축키

부록 A1

출력 스타일 ≠ Structured output

비슷해 보이지만 보장 수준이 완전히 다른 계층이다.

Output style--json-schema
계층시스템 프롬프트디코딩 제약
강제력없음 — 경향스키마 준수
대상사람이 읽는 대화스크립트가 파싱할 데이터
모드인터랙티브headless (-p)

진짜 structured output은 JSON 스키마를 문법으로 컴파일해 토큰 생성 단계에서 제약한다. 복잡한 스키마일수록 문법이 커져 API가 복잡도 제한을 걸어둘 정도.

안티패턴 — "출력 스타일로 JSON만 내보내게 하자". 스타일은 세션 프롬프트일 뿐이라 한 번씩 설명을 덧붙이면 파이프라인이 깨진다. 파싱할 데이터는 --json-schema, 사람이 읽을 화면은 output style.

부록 A2

claude -p도 같은 harness다

Agent SDK가 Claude Code를 구동하는 것과 동일한 도구 · 에이전트 루프 · 컨텍스트 관리를 제공한다. --bare 없이 돌리면 인터랙티브와 같은 컨텍스트를 로드한다.

인터랙티브-p
권한 시작 모드플랜별 기본값모든 플랜에서 Manual
workspace trust다이얼로그없음
슬래시 커맨드전부터미널 전용 제외
CI 보안 포인트. --bare 없는 -p는 신뢰한 적 없는 폴더에서도 그 프로젝트의 .claude/settings.json hook을 실행하고 .mcp.json 서버에 연결한다. trust 다이얼로그도, 서버별 승인 프롬프트도 없이.
--bare는 향후 릴리스에서 -p의 기본값이 될 예정. 단 OAuth · 키체인을 읽지 않으므로 ANTHROPIC_API_KEY 필요.

부록 A3

Status line — 또 하나의 출력 인터페이스

모든 프로그램에는 입구(stdin)와 출구(stdout)가 하나씩 있다. cat log.txt | grep error에서 |가 앞의 출구를 뒤의 입구에 꽂는 것. 상태줄이 딱 그 구조다.

Claude Code ──(세션 JSON)──> [내 스크립트] ──(텍스트)──> 상태줄
                  stdin                        stdout

input=$(cat) = 입구로 들어온 것 전부 읽기
echo "..." = 출구로 내보내기

API 토큰을 전혀 쓰지 않는다. 로컬 실행이다.

캐싱은 문서 권장사항

느리면 갱신이 막히고, 실행 중 새 갱신이 오면 취소되고, 출력이 없으면 상태줄이 빈칸이 된다. 300ms 디바운스.

캐시 키 함정. $$나 os.getpid() 같은 프로세스 ID는 매 호출마다 바뀌어 캐시를 무력화한다. JSON의 session_id를 써라 — 세션 수명 동안 안정적이고 세션마다 고유하다.
