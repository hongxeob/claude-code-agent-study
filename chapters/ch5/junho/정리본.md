## 1. 출력 인터페이스의 위치

Claude Code를 커스터마이징하는 수단은 여러 개다. 결정적 차이는 **어느 계층에 끼어드는가**.

```
┌─────────────────────────────────────────────────────────┐
│  시스템 프롬프트                                          │
│   ├── 내장 엔지니어링 지시문 (기본)                        │
│   ├── Output Style        ← 대체 가능 ★                  │
│   └── --append-system-prompt / --system-prompt (headless)│
├─────────────────────────────────────────────────────────┤
│  대화 계층                                                │
│   ├── CLAUDE.md            ← 유저 메시지로 주입, 덧붙이기만  │
│   └── Skills / Slash commands ← 호출 시점에 주입           │
├─────────────────────────────────────────────────────────┤
│  별도 컨텍스트                                            │
│   └── Subagents            ← 자체 시스템 프롬프트로 분리     │
└─────────────────────────────────────────────────────────┘
```

역할 분리:

| 목적 | 수단 |
|---|---|
| 지식·컨텍스트 주입 | CLAUDE.md |
| 워크플로 | Skill / Slash command |
| **역할·톤·출력 형식** | **Output Style** |
| 작업 격리 | Subagent |

공식문서의 정의: 출력 스타일은 Claude가 *무엇을 아는지*가 아니라 *어떻게 응답하는지*를 바꾼다. 시스템 프롬프트를 수정해 역할·톤·출력 형식을 지정한다. 매 턴 같은 voice나 format을 반복 요구하고 있다면 그때가 쓸 때다.

반대로 프로젝트 규약이나 코드베이스 관련 지시는 CLAUDE.md를 쓰라고 문서가 명시적으로 선을 긋고 있다.

### 1-1. 시스템 프롬프트 vs 유저 메시지 — 뭐가 다른가

스터디에서 나온 질문.

#### 먼저, 흔한 오해 두 가지

> ⚠️ **"CLAUDE.md는 대화가 길어지면 뒤로 밀려서 희석된다"** → **틀렸다.**
> 시스템 프롬프트가 0번, CLAUDE.md가 1번 자리다. **둘 다 맨 앞이다.**
> 3턴이든 30턴이든 CLAUDE.md는 여전히 대화의 맨 앞이고, 현재 생성 지점으로부터의 거리는
> 시스템 프롬프트와 똑같이 멀어진다. **위치로는 둘을 구분할 수 없다.**
>
> (뒤로 밀리는 건 **hook의 prompt injection**이다. 대화 중간에 텍스트를 끼워넣으니까.
> 6장 deprecation 소동에서 "몇 턴 지나면 힘을 잃는다"고 한 대상이 이쪽이지 CLAUDE.md가 아니다.)

> ⚠️ **"시스템 프롬프트는 세션당 1번만 전송된다"** → **틀렸다.**
> LLM API는 stateless라 모델은 이전 대화를 기억하지 못한다. **매 턴 전체를 다시 보낸다.**
> "1회"인 것은 **조립**이지 **전송**이 아니다. → 2-(2)절 참조.

#### 실제 차이

**(1) 역할 의미론 — 이게 본질이다**

API에서 시스템 프롬프트는 `system`이라는 **별도 필드**다. 메시지 배열 안에 있는 게 아니다.
모델은 학습 단계에서 두 역할을 다르게 취급하도록 훈련된다.

| 역할 | 모델이 받아들이는 방식 |
|---|---|
| `system` | 운영자가 정한, 협상 불가능한 설정 |
| `user` | 사용자의 요청 — 밀어낼 수도, 우선순위를 낮출 수도 있는 대상 |

**위치가 아니라 역할 라벨이 차이를 만든다.**

**(2) 교체 가능 여부**

CLAUDE.md는 구조적으로 덧붙이기만 가능하다. 기존 지시문 뒤에 붙는 텍스트다.
Output style은 시스템 프롬프트의 일부를 **들어내고 그 자리를 차지**할 수 있다.
→ "코딩하지 마"를 CLAUDE.md에 아무리 써도 원래 엔지니어링 지시문은 여전히 거기 있다.

**(3) 캐시 위치**

시스템 프롬프트는 캐시된 프리픽스의 맨 앞이다. 바꾸면 그 뒤 전부가 무효화될 자리라, Claude Code는 아예 세션 중 재로드를 안 하는 쪽을 택했다.

#### 그런데 컴팩션에서는 CLAUDE.md가 오히려 강하다

확인해보면 직관과 반대인 사실이 나온다. **루트 CLAUDE.md는 컴팩션을 살아남는다.**
새 윈도우로 다시 읽혀 들어와서 프로젝트 레벨 지시가 그대로 복구된다.
문서도 컴팩션을 넘어 유지되어야 하는 규칙은 `paths:` 프론트매터를 떼고 **프로젝트 루트 CLAUDE.md로 옮기라**고 권한다.

살아남지 **못하는** 것:

| 대상 | 컴팩션 이후 |
|---|---|
| **스코프 룰** (`paths:` 프론트매터로 특정 파일에 걸린 규칙) | 사라짐. 뭔가가 다시 트리거해야 돌아옴 → 에이전트의 다음 행동이 스코프에 안 맞으면 **방금까지 따르던 규칙 없이 움직인다** |
| **대화 중에 타이핑한 지시** | 요약이 남긴 만큼만 |
| **hook·도구 출력으로 주입된 컨텍스트** | 원문 소실, 요약의 패러프레이즈만 |
| **Skill 본문** | 재주입되나 크면 **잘림**. 잘릴 때 앞부분을 남기므로 SKILL.md 위쪽에 중요한 지시를 둘 것 |

> 💡 **실무 규칙: 규칙을 수명으로 분류하라.**
> 세션 전체에 걸쳐 유지돼야 하는 것 → 루트 CLAUDE.md
> 스코프 룰은 ephemeral로 취급 — 에이전트가 다시 발견해도 되는 파일별 디테일용이지, 불변식용이 아니다.
> 검증법: `/compact`를 수동으로 돌려보고 신경 쓰는 규칙을 아직 지키는지 확인.

#### 최종 정리

| | Output style | 루트 CLAUDE.md | 스코프 룰 / 대화 중 지시 |
|---|---|---|---|
| 위치 | `system` 필드 (배열 밖) | 대화 맨 앞 | 대화 중간 |
| 역할 라벨 | `system` | `user` | `user` |
| 내장 지시문 대체 | **가능** | 불가 | 불가 |
| 컴팩션 생존 | 생존 | **생존 (재주입)** | 소실 |

> **한 줄 요약**
> CLAUDE.md = "이것도 알아둬"
> Output style = "너는 이런 존재야"

## 2. 핵심 개념 4가지

### (1) 커스텀 스타일은 "추가"가 아니라 기본적으로 "대체"다

**챕터 5에서 가장 중요한 함정.**

커스텀 출력 스타일은 `keep-coding-instructions: true`를 켜지 않는 한, Claude Code에 내장된 소프트웨어 엔지니어링 지시문을 빼버린다.

- 변경 범위를 어떻게 잡을지
- 주석을 어떻게 쓸지
- 작업을 어떻게 검증할지

증상: 페르소나 스타일 하나 만들고 나서 갑자기 Claude가 코딩을 못한다. 변경을 반쯤 하다 말고, 검증을 건너뛰고, 엉뚱한 곳에 주석을 단다. **경고도 안 뜬다.** 모델 문제가 아니라 스타일이 지시문을 지운 것.

```yaml
keep-coding-instructions: true   # 이 한 줄로 방지
```

판단 기준:
- 코딩은 계속하고 표현만 바꾼다 → `true`
- 아예 다른 직군 에이전트로 쓴다 (문서 작성기, 데이터 분석가) → 생략

### (2) 조립은 1회, 전송은 매 턴

가장 헷갈리는 부분이라 정확히 짚고 간다.

**LLM API는 stateless다.** 모델은 이전 대화를 기억하지 못하고, 매 요청을 처음 보는 것처럼 받는다. 그래서 매 턴 전체를 다시 보낸다.

```
1턴 요청:  [시스템 프롬프트] + [유저1]
2턴 요청:  [시스템 프롬프트] + [유저1] + [응답1] + [유저2]
3턴 요청:  [시스템 프롬프트] + [유저1] + [응답1] + [유저2] + [응답2] + [유저3]
            ^^^^^^^^^^^^^^^^
            매번 똑같이 맨 앞에 실린다
```

대화가 길어질수록 요청이 커지고 컨텍스트 윈도우가 차는 게 이 구조 때문이다.

**그럼 "1회"인 건 뭔가 — 문자열을 만드는 작업이다.**

세션 시작 시 Claude Code가 output style 파일·settings·내장 지시문을 읽어 시스템 프롬프트 문자열 하나를 조립한다. 그 뒤로는 **그 문자열을 그대로 재사용**할 뿐, 파일을 다시 읽지 않는다.

```
세션 시작 ─┬─> 파일 읽기 → 시스템 프롬프트 조립   ← 여기가 1회
           ├─> 1턴: [조립된 문자열] 전송
           ├─> 2턴: [조립된 문자열] 전송          ← 매번
           └─> 3턴: [조립된 문자열] 전송
```

→ 세션 중간에 `outputStyle`을 바꿔도 안 먹히는 이유가 이것이다. 전송이 안 돼서가 아니라, **이미 만들어진 문자열이 계속 쓰이기 때문**. `/clear`가 필요한 이유.

**캐시 관점**: 세션 중간에 `/config`나 `outputStyle` 설정으로 바꾸면 **캐시를 무효화하지도 않지만 적용되지도 않는다.**

매 턴 다시 보낸다면 매 턴 다시 과금되나? → 시스템 프롬프트는 **내용이 동일하고 위치가 맨 앞**이라 캐시가 가장 잘 걸리는 조건이다. 첫 요청에서 cache write, 이후로는 cache read로 훨씬 싸게 처리된다. 문서가 출력 스타일의 입력 토큰 증가를 두고 "세션 첫 요청 이후에는 프롬프트 캐싱이 비용을 줄여준다"고 한 게 이 얘기.

역으로 **맨 앞에 있다는 건 바꾸면 그 뒤 전부가 무효화된다는 뜻**이기도 하다. 모델을 바꿀 때 캐시 경고가 뜨는 이유.

→ "저장은 됐는데 안 먹는다"의 90%는 이것.

### (3) 메인 에이전트 루프에만 적용된다

서브에이전트는 자기 시스템 프롬프트로 돌기 때문에 출력 스타일이 서브에이전트 응답에 영향을 주지 않는다. 예외는 **fork** — 부모의 전체 시스템 프롬프트를 그대로 상속받기 때문.

실무 함의: "코드리뷰는 무조건 표 형식으로" 스타일을 만들어도, 리뷰를 서브에이전트에 위임하는 순간 포맷이 깨진다.

### (4) 토큰 비용

- **입력**: 시스템 프롬프트에 지시가 추가되니 늘어남. 단 세션 첫 요청 이후엔 프롬프트 캐싱이 비용을 줄여줌.
- **출력**: Explanatory·Learning은 설계상 Default보다 긴 응답. Concise는 반대.

## 3. 내장 스타일 5종

| 스타일 | 동작 | 쓸 때 |
|---|---|---|
| **Default** | 기존 엔지니어링 시스템 프롬프트 | 기본 |
| **Proactive** | 즉시 실행. 사소한 결정은 멈춰 묻는 대신 합리적으로 가정. 계획보다 행동 선호. auto 모드보다 강한 자율 실행 지시이면서 permission mode는 건드리지 않음 — 무엇이 승인 없이 실행되는지는 여전히 permission mode가 결정 | 반복적·저위험 작업 배치 |
| **Concise** | 결론부터. 서론·중계 설명 생략. 단 엔지니어링 작업 자체는 Default만큼 철저하고, 설명을 요청하면 온전히 답함. 에러 리포트·보안 경고·파괴적 작업 확인은 항상 전문 유지. **v2.1.237+** | 숙련자 일상 개발 |
| **Explanatory** | 작업 중간에 교육적 "Insights"를 삽입. 구현 선택과 코드베이스 패턴을 이해시킴 | 온보딩, 낯선 레포 |
| **Learning** | Insights 공유 + **작고 전략적인 코드 조각을 직접 짜라고 요구.** 코드에 `TODO(human)` 마커를 남김 | 학습, 스터디 |

> 💡 **스터디 활용**: Learning 모드의 `TODO(human)`을 그대로 스터디 도구로 쓸 수 있다.
> 담당 파트를 `TODO(human)`으로 남기게 하고 다음 주에 채워오는 방식.

## 4. 실습 가이드

### Step 0 — 버전 확인 (필수)

```bash
claude --version
```

- 독립 `/output-style` 명령: **v2.1.73 deprecated → v2.1.91 제거**
- Concise 스타일: **v2.1.237 이상**

### Step 1 — 내장 스타일 적용

```bash
/config          # → Output style 메뉴에서 선택
```

터미널에서 선택하면 로컬 프로젝트 레벨 `.claude/settings.local.json`에 저장된다.
데스크톱 앱에서는 메뉴 대신 Settings > Claude Code가 열리므로 설정 파일을 직접 편집.

또는 설정 파일 직접 수정:

```json
{ "outputStyle": "Explanatory" }
```

**그리고 `/clear` 또는 재시작.** 안 하면 안 바뀐다.

### Step 2 — 커스텀 스타일 파일 위치

| 스코프 | 경로 | 범위 |
|---|---|---|
| User | `~/.claude/output-styles/` | 모든 프로젝트 |
| Project | `.claude/output-styles/` | 해당 레포 (git 커밋 가능) |
| Managed policy | managed settings 디렉터리 내 `.claude/output-styles/` | 조직 전체 배포 |

- 프론트매터에 `name`을 안 쓰면 **파일명이 스타일 이름**이 된다.
- 프로젝트 스타일은 작업 디렉터리부터 레포 루트까지의 모든 `.claude/output-styles/`에서 로드되고, 같은 이름이 여러 곳에 있으면 **작업 디렉터리에 가장 가까운 것이 이긴다** (모노레포 유용, v2.1.178+).
- 플러그인도 `output-styles/` 디렉터리로 스타일을 배포할 수 있다.

### Step 3 — 프론트매터 (4개 필드)

| 필드 | 의미 | 기본값 |
|---|---|---|
| `name` | 스타일 이름 (파일명과 다를 때) | 파일명 상속 |
| `description` | `/config` 피커에 표시될 설명 | — |
| `keep-coding-instructions` | 내장 엔지니어링 지시문 유지 | **`false`** ⚠ |
| `force-for-plugin` | 플러그인 전용. 플러그인이 켜지면 사용자 선택 없이 자동 적용되며 사용자의 `outputStyle` 설정을 덮어씀. 여러 플러그인이 설정하면 먼저 로드된 것 사용 | `false` |

공식문서 예시:

```markdown
---
name: Diagrams first
description: Lead every explanation with a diagram
keep-coding-instructions: true
---

When explaining code, architecture, or data flow, start with a Mermaid
diagram showing the structure, then explain in prose.

## Diagram conventions

Use `flowchart TD` for control flow and `sequenceDiagram` for request paths.
Keep diagrams under 15 nodes.
```

### Step 4 — 검증 & 트러블슈팅

| 증상 | 원인 / 해결 |
|---|---|
| 피커에 스타일이 안 보임 | 재시작 (스타일은 세션 시작 시 열거됨). 그래도 없으면 파일이 `output-styles/` **바로 아래**에 있는지(하위 디렉터리 X), `.md`로 끝나는지, 올바른 config 디렉터리인지 확인 |
| 스타일은 보이는데 settings.json이 선택 못 함 | `outputStyle` 값이 프론트매터 `name`과 **대소문자까지** 일치해야 함 |
| 위와 증상 동일한데 원인이 다름 | JSON 문법 오류. `claude doctor`가 파싱 실패 파일을 알려줌 — **이걸 먼저 돌려라** |
| 비기본 config 디렉터리 사용 | `CLAUDE_CONFIG_DIR` 설정 시 유저 레벨 경로도 따라감(예: `~/.claude-thomas/output-styles/`). 각 config 디렉터리마다 파일 사본 + settings.json 항목이 별도로 필요 |

### Step 5 — 스타일 잘 쓰는 법 (커뮤니티 정론)

잘 만든 terse 스타일이 통하는 이유 두 가지:

1. **규칙이 기계적이다.** "포인트당 한 줄", "em dash 금지", "caveat는 최대 하나, 마지막 줄에"는 검증 가능하다. "간결하게"는 아니다.
2. **정직성을 명시적으로 예외 처리한다.** 간결함은 단어 수의 문제이므로, 실패·건너뛴 단계·검증 안 된 수치는 여전히 말하게 한다. 이 조항이 없으면 terse 스타일은 군더더기와 함께 caveat까지 버린다.

> **작성 원칙: 세어볼 수 있는 규칙으로 쓰고, 줄이면 안 되는 것을 명시적으로 카브아웃한다.**

톤만 살짝 바꾸고 싶은 거라면 CLAUDE.md가 리스크가 낮은 선택이다 — 내장 코딩 프롬프트를 절대 밀어내지 않으니까. 스타일 규칙은 CLAUDE.md에서도 동작하고, 출력 스타일과 **대체가 아니라 누적**된다.

## 8. [확장] 출력 스타일 ≠ Structured Output

"약간 structured output 같은 거네"라는 질문이 나왔는데, **보장 수준이 완전히 다른 계층**이다.

| | Output style | `--json-schema` |
|---|---|---|
| 계층 | 시스템 프롬프트 | **디코딩 제약** |
| 강제력 | 없음 (경향) | 스키마 준수 |
| 대상 | 사람이 읽는 대화 | 스크립트가 파싱할 데이터 |
| 모드 | 인터랙티브 | headless (`-p`) |

- Output style은 프롬프트에 문장을 얹는 것뿐. 안 지켜도 막을 방법이 없다. (그래서 문서가 "Default가 아닌 스타일일 때 대화 중에 계속 상기시킨다"고 적어둔 것 — 상기시켜야 한다는 건 잊을 수 있다는 뜻)
- 진짜 structured output은 JSON 스키마를 **문법(grammar)으로 컴파일**해서 토큰 생성 단계에서 제약한다. 복잡한 스키마일수록 문법이 커져서 API가 복잡도 제한까지 걸어둘 정도.

```bash
claude -p "src/auth.ts 보안 이슈 리뷰" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"issues":{"type":"array","items":{"type":"string"}},"severity":{"type":"string","enum":["low","medium","high"]}},"required":["issues","severity"]}'
```

구조화된 결과는 응답의 `structured_output` 필드에 담긴다.

**버전 함정**: 스키마가 유효하지 않으면 `Error: --json-schema is not a valid JSON Schema` + 검증기 진단. `"format": "email"` 같은 키워드는 받아주지만 어노테이션으로만 취급하고 강제하지 않는다. **v2.1.205 이전에는 유효하지 않은 스키마를 조용히 무시하고 비구조화 텍스트를 반환했다.**

> **안티패턴: "출력 스타일로 JSON만 내보내게 하자"**
> 스타일은 세션 프롬프트일 뿐이라 한 번씩 설명을 덧붙이면 파이프라인이 깨진다.
> 파싱할 데이터는 `--json-schema`, 사람이 읽을 화면은 output style.

## 9. [확장] `claude -p`는 같은 harness인가?

**그렇다.** Agent SDK가 Claude Code를 구동하는 것과 동일한 도구·에이전트 루프·컨텍스트 관리를 제공하고, `claude -p`는 그 SDK를 CLI로 쓰는 것이다. `--bare` 없이 돌리면 인터랙티브 세션과 **같은 컨텍스트**를 로드한다.

| | 인터랙티브 | `-p` |
|---|---|---|
| 권한 시작 모드 | 플랜별 기본값 | 모든 플랜에서 **Manual** → `--permission-mode` 직접 지정 필요 |
| workspace trust | 다이얼로그 | **없음** |
| 슬래시 커맨드 | 전부 | 터미널 전용(`/login` 등) 제외. 스킬은 프롬프트에 `/skill-name`으로 넣으면 확장 |
| 출력 | TUI | `text` / `json` / `stream-json` |

### ⚠ CI 보안 포인트

`--bare`는 hooks, skills, 커스텀 커맨드, 서브에이전트, 플러그인, MCP 서버, auto memory, CLAUDE.md의 자동 탐색을 전부 건너뛴다.

반대로 말하면 — **`--bare` 없는 `-p`는 신뢰한 적 없는 폴더에서도 그 프로젝트의 `.claude/settings.json` hook을 실행하고 `.mcp.json` 서버에 연결한다. trust 다이얼로그도, 서버별 승인 프롬프트도 없이.** PR에서 임의 코드를 체크아웃해 도는 CI라면 실질적 공격 표면이다.

`--bare`는 스크립트/SDK 호출에 권장되는 모드이고, **향후 릴리스에서 `-p`의 기본값이 될 예정**. 단 bare 모드는 OAuth 자격증명·시스템 키체인을 읽지 않으므로 `ANTHROPIC_API_KEY`가 필요하다.

## 10. [확장] Status line — 또 하나의 출력 인터페이스

### 원리: 유닉스 파이프

모든 프로그램에는 입구(stdin)와 출구(stdout)가 하나씩 있다. `cat log.txt | grep error`에서 `|`가 앞 프로그램의 출구를 뒤 프로그램의 입구에 꽂는 것.

```
Claude Code ──(세션 JSON)──> [내 스크립트] ──(텍스트)──> 상태줄 표시
                stdin                        stdout
```

- `input=$(cat)` = "입구로 들어온 것 전부 읽기"
- `echo "..."` = "출구로 내보내기"
- Claude Code는 그 텍스트를 화면에 그릴 뿐 → **API 토큰을 전혀 안 쓴다** (로컬 실행)

### 설정

```json
{
  "statusLine": {
    "type": "command",
    "command": "~/.claude/statusline.sh",
    "padding": 2
  }
}
```

`/statusline show model name and context percentage with a progress bar` 처럼 자연어로 시키면 Claude가 스크립트를 생성하고 설정까지 갱신해준다. 삭제는 `/statusline delete`.

### 갱신 시점

세션 시작 시 1회(resume 포함). 이후 다음 상황에서 재실행:
- 새 assistant 메시지 도착
- `/compact` 완료
- permission mode 변경 / vim mode 토글
- `command` 설정 변경
- `refreshInterval` 타이머 (설정한 경우, 최소 1초)
- rate limit 창이 `resets_at`에 도달
- warm 프롬프트 캐시가 `expires_at`에 도달

**300ms 디바운스.** 실행 중에 새 갱신이 오면 진행 중인 스크립트는 **취소된다.**

### 성능 — 캐싱은 문서 권장사항이 맞다

스크립트가 활성 세션 동안 자주 실행되므로 `git status` 같은 명령은 큰 저장소에서 느려질 수 있다. 이유 셋:
1. 느리면 상태줄 갱신이 완료될 때까지 막힘
2. 실행 중 새 갱신 오면 in-flight 스크립트 취소
3. 비정상 종료하거나 출력이 없으면 상태줄이 빈칸

**캐시 키 함정**: `$$`, `os.getpid()`, `process.pid` 같은 프로세스 ID는 **매 호출마다 바뀌어서 캐시를 무력화한다.** JSON의 `session_id`를 써라 — 세션 수명 동안 안정적이고 세션마다 고유해서, 다른 저장소의 동시 세션끼리 git 상태를 섞어 읽지 않는다.

```bash
CACHE_FILE="/tmp/statusline-git-cache-$SESSION_ID"
CACHE_MAX_AGE=5  # seconds
```

### 주요 JSON 필드

| 필드 | 내용 |
|---|---|
| `model.id`, `model.display_name` | 현재 모델 |
| `workspace.current_dir`, `project_dir`, `added_dirs` | 디렉터리 |
| `cost.total_cost_usd` | 세션 추정 비용 (클라이언트 계산, 실청구와 다를 수 있음) |
| `context_window.used_percentage` | 컨텍스트 사용률 (**input 토큰만**으로 계산, output 미포함) |
| `rate_limits.five_hour / seven_day` | Pro·Max 구독자만, 첫 API 응답 이후 |
| `prompt_cache.warm / hit_ratio` | 캐시 상태 (v2.1.251+) |
| `effort.level` | low/medium/high/xhigh/max |
| `output_style.name` | **현재 출력 스타일 ← 이 장과 연결** |
| `session_id` | 캐시 키로 쓸 것 |

### 테스트 & 트러블슈팅

```bash
echo '{"model":{"display_name":"Opus"},"workspace":{"current_dir":"/home/user/project"},"context_window":{"used_percentage":25},"session_id":"test-abc"}' | ./statusline.sh
```

- 안 뜸 → `chmod +x` 확인이 1순위. stdout으로 출력하는지(stderr 아님) 확인
- `claude --debug`가 세션 첫 실행의 exit code와 stderr를 로깅
- **workspace trust 필요**: 셸 명령을 실행하므로 hook과 동일한 trust 규칙. 수락 전에는 상태줄이 빈칸이고 debug 로그에 `Status line command skipped: workspace trust not accepted`
- 조직이 `allowManagedHooksOnly`를 설정하면 **경고 없이 사라진다** — 관리자에게 문의

## 11. [확장] 단축키 & Rewind

### Esc Esc는 조건부다

- 입력창에 **텍스트가 있으면** → 초안을 지우고 히스토리에 저장 (`Up`으로 복원)
- 입력창이 **비어 있으면** → rewind 메뉴

rewind 메뉴 선택지 3종:
1. **Restore code and conversation** — 코드+대화 모두 되돌림
2. **Restore conversation** — 대화만, 코드는 현재 유지
3. **Restore code** — 코드만, 대화는 유지

코드 관련 두 옵션은 해당 체크포인트에 되돌릴 파일 변경이 있을 때만 나타난다.

**한계**: 심볼릭/하드 링크된 파일은 되감지 않고 건너뛰며 경고를 띄운다. dotfile 매니저가 심링크한 설정, pnpm이 하드링크한 파일이 해당.

### 자주 쓰는 단축키

| 키 | 동작 |
|---|---|
| `Esc` | 응답/도구 호출 중단. 지금까지 작업은 유지 |
| `Esc` `Esc` | 초안 지우기 또는 rewind |
| `Shift+Tab` | 권한 모드 순환 (`default`→`acceptEdits`→`plan`→…) |
| `Ctrl+B` | 실행 중 작업 백그라운드로 (**tmux는 두 번**) |
| `Ctrl+O` | 트랜스크립트 뷰어 토글 |
| `Ctrl+G` | 프롬프트를 기본 편집기에서 열기 |
| `Ctrl+S` | 프롬프트 임시 보관 / 복원 |
| `Ctrl+R` | 명령 히스토리 역방향 검색 |
| `Ctrl+L` | 화면 다시 그리기 |
| `Ctrl+X Ctrl+K` | 백그라운드 서브에이전트 전부 중지 (3초 내 두 번) |
| `!` | 셸 모드 — 출력을 컨텍스트에 넣고 Claude가 응답 |
| `/btw` | 대화 히스토리에 안 남는 사이드 질문 |
| `?` (빈 입력) | 단축키 도움말 |
| `Option/Alt+P` | 모델 전환 (프롬프트 유지) |
| `\` + `Enter` | 멀티라인 입력 (모든 터미널에서 동작) |

> `Ctrl+C`는 중단용이 아니다. 실행 중이면 중단, 아니면 첫 press는 입력 클리어, 두 번째는 종료.
> **중단은 `Esc`.**
