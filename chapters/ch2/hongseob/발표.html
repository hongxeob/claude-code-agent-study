1. settings.json은 정해진 스펙인가 — 임의 key 실험

의문: key에 스펙이 있나, 아무거나 적어도 세팅되나?

$ claude -p "OK만 답해" --settings '{"홍섭_임의테스트키_xyz":"hello"}'
→ exit 0,  출력: OK,  경고 없음

결론: 미정의 key는 거부되지 않고 그냥 무시됐다. key는 공식 스펙(model·hooks·env …)이 정해져 있고, 편집기에 $schema를 넣으면 미정의 key를 편집 단계에서 잡아준다.

(공식문서는 user/project/local을 strict라 하지만, 미정의 key가 "검증 실패"로 취급되진 않았음 — 스키마가 추가 속성 허용.)

2. 워크플로 핵심 — 탐색 → 분석 → 심화

탐색→ 분석→ 심화 분석 + 코드 작업

예시 — ch1 @경로 실험(실제 이렇게 진행)

  1. 탐색 — 어떤 파일이 큰지 파악 (300줄 더미 만들어 크기 측정)
  2. 분석 — @경로 vs 풀경로 토큰 비교 (10,500 vs 175)
  3. 심화+코드 — "큰 파일은 풀경로" 결론 → 정리본·발표에 반영

핵심: 한 번에 다 시키지 않고 앞 단계 결과를 다음 단계 입력으로 넘긴다.

5. 스프링부트 .env가 빌드에서 안 읽히던 문제

클로드 코드로 gradle bootRun/java -jar 돌릴 때 .env 값이 서버에 안 들어감. 왜?

(a) cat .env          → 읽힘        # . prefix는 문제 아님
(b) 새 셸에서 echo $FOO → []          # 셸이 .env 자동 로드 안 함
(c) source .env 후      → bar         # 로드하면 들어감
원인 ① 셸

셸이 .env 자동 로드 안 함

빌드 명령 도는 셸은 명시적 source/export 없으면 .env를 안 읽음.

원인 ② 스프링

스프링도 .env 안 읽음

Spring은 application.yml·OS 환경변수·시스템 프로퍼티만 봄. .env는 spring-dotenv 없으면 무시. IDE는 실행 구성이 넣어줬던 것.

정답

settings.json의 env에 넣으면 됨 — 공식문서: "모든 세션과 모든 subprocess에 주입".

{ "env": { "SPRING_DATASOURCE_URL": "jdbc:...",
           "SPRING_PROFILES_ACTIVE": "local" } }

단, yaml 파일에 써넣는 게 아니다 (IDE도 마찬가지). 프로세스 OS 환경변수로 넣을 뿐, 스프링이 실행 시점에 읽어 dev/local 값을 구성:

  1. 프로파일 선택 — SPRING_PROFILES_ACTIVE=dev → application-dev.yml 활성화
  2. 런타임 오버라이드 — env가 yaml보다 우선순위 높음. 같은 키면 yaml 값도 덮어씀
  3. placeholder 치환 — yaml의 ${SPRING_DATASOURCE_URL} 자리에 env 값 주입

우선순위(높→낮): 실행 인자 > OS 환경변수 > application-{profile}.yml > application.yml.

클로드 코드로 서버 실행 — 2가지 방법

⚠️ .env엔 실 자격증명이 들어감 — 커밋되는 파일엔 절대 넣지 말 것.

A. settings env

값을 settings.local.json으로

.env의 KEY=VALUE → JSON으로 변환해 gitignore되는 .claude/settings.local.json의 env에.

세팅 후 자동 주입. 단점: .env와 이중 관리.

B. source .env (추천)

빌드 명령에서 로드

set -a; . ./.env; set +a \
  && ./gradlew bootRun

.env 하나만 유지, 이중관리 없음. (또는 spring-dotenv 의존성)

"서버 실행해줘" 자연어로 B를 자동 실행시키려면

프로젝트 CLAUDE.md에 규칙 한 줄 → 매 세션 자동 로드되므로 자연어만으로 Claude가 명령을 붙여 실행:

## 로컬 서버 실행
"서버 실행"/"bootRun" 요청 시 항상 아래로 실행 (.env 주입):
`set -a; . ./.env; set +a && ./gradlew bootRun`

반복 명령을 스킬/슬래시 커맨드(/run-server)로 만들어도 동일.

팀원과 공유하기 싫으면 — 위 규칙을 CLAUDE.md 대신 개인 전용 파일에:

파일범위공유
./CLAUDE.md이 프로젝트팀 전체 (git 커밋)
./CLAUDE.local.md이 프로젝트나만 (.gitignore)
~/.claude/CLAUDE.md모든 프로젝트나만

CLAUDE.local.md도 매 세션 자동 로드. ~/.claude/CLAUDE.md는 모든 프로젝트에 적용돼 프로젝트별 서버 명령엔 너무 넓음. (worktree 여러 개면 홈 파일을 @~/.claude/...로 import)

정리

  • settings.json은 정해진 스펙 + 5단 위계(관리자가 최상위).
  • 퀄리티는 탐색→분석→심화의 단계 이어달리기에서 나온다.
  • 작게 쪼개고 자동 검증 루프를 건다 — 프롬프트보다 루프.
  • 스프링 .env 미주입 = 셸·스프링 둘 다 안 읽어서. 정답은 settings.json env.
