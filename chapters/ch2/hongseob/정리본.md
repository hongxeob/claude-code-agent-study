# 2장 — 워크플로 (홍섭)

> 스터디 발표용 개인 정리본. 원 노트를 구조화하고, 실험 3개(임의 key·`.env`·`settings env`)와 공식문서 조사로 확정한 버전.

## 1. settings.json은 뭐였나 + 임의 key 실험

초창기엔 `settings.json`이 뭔지 몰랐음. 의문: **key에 정해진 스펙이 있나? 임의로 적으면 알아서 세팅되나?**

**적용예시 (실측):** 내 `~/.claude/settings.json` key들 — `model`, `hooks`, `statusLine`, `enabledPlugins`, `theme`, `skipDangerousModePermissionPrompt` 등. 전부 **공식 스펙 key**. 임의 key 아님.

**실험 (안전 — 유저 설정 안 건드리고 별도 파일로):**
```
claude -p "OK만 답해" --settings '{"홍섭_임의테스트키_xyz":"hello"}'
→ exit 0, "OK" 출력, 경고 없음
```
- **결론:** 미정의 key를 넣어도 **거부되지 않고 그냥 실행됨(무시).**
- 단, 공식문서는 user/project/local 설정을 **strict**(검증 실패 시 파일 통째 거부)라고 함. 미정의 key는 그 "검증 실패"로 취급되진 않았다(스키마가 추가 속성 허용). 편집기에서 `$schema` 넣으면 미정의 key를 편집 단계에서 잡아줌.

## 2. 워크플로 핵심 — 탐색 → 분석 → 심화

작업 퀄리티를 내는 순서:

```
탐색  →  분석  →  (앞 단계 활용) 심화 분석 + 코드 작업
```

**예시 시나리오 — ch1 `@`경로 토큰 실험(실제로 이렇게 진행했음):**

1. **탐색** — 어떤 파일이 큰지 파악 (300줄 더미 파일 만들어 크기 측정)
2. **분석** — `@경로` vs `풀경로` 토큰 차이 측정 (10,500 vs 175)
3. **심화 + 코드 작업** — "큰 파일은 풀경로" 결론 도출 → 정리본·발표에 반영

→ 한 번에 다 시키는 게 아니라, **앞 단계 결과를 다음 단계 입력으로** 넘기는 게 핵심.

## 3. 점진 개발 단위 + 피드백 루프 (팀 질문 + 조사)

**팀에 던질 질문:** 다들 얼마나 작은 단위로 작업하나? 정량 기준 두나? 어떤 자동 검증 수단을 쓰나?

**내가 조사해 온 것:**
- **작업 단위** — "몇 줄" 같은 정량 기준보다 **한 번에 검증 가능한 최소 변경(atomic sub-requirement)** 으로 쪼개는 게 정설. Claude Code는 plan mode로 **탐색과 실행을 분리**하고 Explore→Plan→Implement→Commit 4단계 권장.
- **자동 검증** — ESLint·Prettier·Vitest·SonarQube 같은 도구가 AI에게 **코칭 신호**가 됨. 스펙 끝에 **e2e 검증 단계**를 둬서 "동작함"을 증명. 핵심 통찰: **좋은 프롬프트보다 좋은 피드백 루프가 더 중요** (여러 번 시도 가능하니까).

## 4. settings.json 위계 (우선순위 높음 → 낮음)

| 순위 | 종류 | 파일 |
|------|------|------|
| 1 | 관리자(엔터프라이즈 정책) | `/Library/Application Support/ClaudeCode/managed-settings.json` |
| 2 | CLI 인자 | `--effort` 등 세션 임시 |
| 3 | 로컬(개인·비공유) | `<repo>/.claude/settings.local.json` (gitignore) |
| 4 | 프로젝트(팀 공유) | `<repo>/.claude/settings.json` (커밋) |
| 5 | 사용자 | `~/.claude/settings.json` |

- 겹치면 **위(관리자)가 이김.** 노트의 "관리자 설정"과 "엔터프라이즈 정책"은 같은 것(`managed-settings.json`).
- **실측:** 내 환경엔 사용자 설정만 있음. 관리자·프로젝트·로컬 없음.

## 5. 스프링부트 .env가 빌드/실행에서 안 읽히던 문제 (정답)

여기서 `.env` = **스프링부트 서버에 주입할 환경변수 파일.** IDE가 아니라 클로드 코드로 빌드/실행시킬 때 이 값들이 안 들어가 매번 수동 입력하던 문제. 가설: 앞의 `.` 때문? / `settings.json`에 env 넣으면 됨?

**원인은 이중이다 — 실험 + 사실:**

```
(a) cat .env        → 읽힘          # . prefix는 문제 아님
(b) 새 셸에서 echo $FOO → []          # 셸이 .env 자동 로드 안 함
(c) source .env 후 echo $FOO → bar   # 로드하면 들어감
```

1. **셸 레이어:** 빌드 명령이 도는 셸은 `.env`를 자동 로드하지 않음(명시적 `source`/`export` 필요). 앞의 `.`은 무관.
2. **스프링 레이어:** **스프링부트도 `.env`를 기본으로 읽지 않음.** Spring은 `application.yml`/`application.properties`, **OS 환경변수**, 시스템 프로퍼티, 실행 인자만 본다(`spring-dotenv` 같은 라이브러리를 따로 넣지 않는 한). IDE에서 됐던 건 IDE 실행 구성이 env를 넣어줬기 때문.

**정답 — settings.json `env`에 넣으면 된다 (공식문서 확인):**
```json
{ "env": { "SPRING_DATASOURCE_URL": "jdbc:...", "SPRING_PROFILES_ACTIVE": "local" } }
```
- 공식문서: `env`는 "**모든 세션과 클로드 코드가 띄우는 모든 subprocess**에 환경변수를 주입". → `gradle bootRun`/`java -jar` 같은 빌드·실행 subprocess가 그 **OS 환경변수**를 가진 채로 돈다.

**중요 — "yaml 파일에 주입"이 아니다 (IDE도 마찬가지):**

`settings.json env`도 IDE도 **yaml 파일을 수정하지 않는다.** 프로세스의 OS 환경변수로 넣을 뿐이고, 스프링이 **실행 시점에** 그걸 읽어 Environment를 구성한다. dev/local에 맞는 값이 뜨는 건 이 3가지 덕분:

1. **프로파일 선택** — `SPRING_PROFILES_ACTIVE=dev` → `application-dev.yml` 자동 활성화.
2. **런타임 오버라이드** — OS 환경변수는 스프링 프로퍼티 우선순위가 yaml보다 **높다**. 같은 키면 `application-dev.yml`의 값도 env가 덮어씀 (relaxed binding: `SPRING_DATASOURCE_URL` → `spring.datasource.url`).
3. **placeholder 치환** — yaml에 `${SPRING_DATASOURCE_URL}`로 잡아뒀으면 그 자리에 env 값이 들어감.

> 스프링 프로퍼티 우선순위(높→낮, 관련분): 실행 인자 > **OS 환경변수** > `application-{profile}.yml` > `application.yml`. 그래서 env가 yaml을 이긴다.

- **실측:** 내 `settings.json`엔 `env` 키 아직 없음 → 도입한다면 **프로젝트 `.claude/settings.json`**(팀 공유, 단 비밀값은 커밋 금지) 또는 **`.claude/settings.local.json`**(gitignore되는 개인 값)에.
- 주의: 이건 `.env` 값을 `settings.json`에 **옮겨 적는 것**이지 `.env` 파일을 자동으로 읽어주는 게 아님.

### 실전 — 클로드 코드로 서버 실행 (.env 주입) 2가지

> ⚠️ `.env`엔 실 자격증명이 들어가므로 **커밋되는 파일에 절대 넣지 말 것.** `.env`는 gitignore, 아래 A도 `settings.local.json`(gitignore)만 사용.

**A. `settings.local.json`의 `env`에 값 이관**
- `.env`의 `KEY=VALUE` → JSON `{"KEY":"VALUE"}`로 변환 (주석·주석처리 줄은 버림).
- `.claude/settings.local.json`(gitignore)에만. `.claude/settings.json`(팀 공유)에 넣으면 유출.
- 세팅 후 모든 subprocess에 자동 주입. **단점: `.env`와 이중 관리.**

**B. 빌드 명령에서 `.env` source (추천 — 이중관리 없음)**
```
set -a; . ./.env; set +a && ./gradlew bootRun
```
- `.env` 하나만 유지. 또는 `spring-dotenv` 의존성으로 스프링이 직접 읽게.

| | A. settings env | B. source .env |
|---|---|---|
| 자동 주입 | O(세팅 후) | O(명령에 포함) |
| 이중 관리 | 있음 | 없음 |
| 유출 위험 | local.json 아니면 큼 | `.env` gitignore면 안전 |

**"서버 실행해줘" 자연어로 B를 자동 실행시키려면 → 프로젝트 `CLAUDE.md`에 규칙 한 줄:**
```md
## 로컬 서버 실행
"서버 실행"/"bootRun" 요청 시 항상 아래로 실행한다 (.env 주입):
`set -a; . ./.env; set +a && ./gradlew bootRun`
```
- `CLAUDE.md`는 매 세션 컨텍스트에 자동 로드됨 → "서버 실행해줘"만 해도 Claude가 이 규칙을 보고 빌드 명령을 붙여 실행한다.
- 반복 명령을 스킬/슬래시 커맨드(`/run-server`)로 만들어도 동일 효과.

**팀원과 공유하기 싫으면 `CLAUDE.local.md` (개인 전용):**

| 파일 | 범위 | 공유 |
|------|------|------|
| `./CLAUDE.md` | 이 프로젝트 | 팀 전체 (git 커밋) |
| `./CLAUDE.local.md` | 이 프로젝트 | **나만** (`.gitignore`에 추가) |
| `~/.claude/CLAUDE.md` | 모든 프로젝트 | 나만 |

- 위 규칙을 `CLAUDE.md` 대신 **`CLAUDE.local.md`**(프로젝트 루트, gitignore)에 넣으면 나만 적용되고 팀원은 안 건드린다. `CLAUDE.local.md`도 `CLAUDE.md`와 똑같이 매 세션 로드됨.
- `~/.claude/CLAUDE.md`는 개인용이지만 **모든 프로젝트**에 적용돼 이런 프로젝트별 서버 명령엔 너무 넓다.
- 함정: `CLAUDE.local.md`는 **worktree마다 따로** 존재. 여러 worktree에서 공유하려면 홈에 파일 두고 `@~/.claude/nova-server.md`로 import.
