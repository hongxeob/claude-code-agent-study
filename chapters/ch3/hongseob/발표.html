한눈에

① 커맨드·스킬 통합의 실체 = 호출 방식 통합. 같은 SKILL.md 포맷, / 직접 호출·자연어 자동 발동 양쪽 다 지원.

② 스킬 3종: 로컬 / 프로젝트 / 팀(배포) — nova-workflow가 팀 배포 실사례.

③ SKILL.md는 200줄·SRP, name은 관례(강제 아님), context/agent/background로 컨텍스트 격리.

④ 토큰 최적화 5원칙으로 스킬 자체의 무게를 줄인다.

커맨드 vs 스킬 — 화이트박스 대 블랙박스

🎚️
White Box
커맨드
사람이 직접 지정 · 직접 제어

  • 실측 — nova-workflow의 commit, pr, handoff
  • 모델 자동호출을 명시적으로 차단 → 커맨드 성격 확정
⬛
Black Box
스킬
클로드가 상황 보고 알아서 선택

사람은 자연어로 말할 뿐, 어떤 스킬이 뽑혀 어떻게 도는지는 클로드 안에서 결정된다.

frontmatter: description에 트리거 문구 밀집
  • 실측 — humanize-korean
  • "AI 티 없애줘"라고만 해도 클로드가 골라 씀
통합의 실체는 호출 방식 통합 — 이제 둘 다 같은 SKILL.md 포맷. 성격은 disable-model-invocation 유무 하나로 갈린다.

스킬 유형 3가지 — 로컬 / 프로젝트 / 팀

유형위치실측 예시
로컬~/.claude/skills/*humanize-korean, commit-push-pr
프로젝트이 레포 .claude/skills/*pre-chapter-prep, mid-study-wrapup
팀(배포)사내 플러그인 마켓플레이스nova-workflow — 18개 스킬 배포
사례

회사 개발팀에 nova-workflow 플러그인을 만들어 배포. nova-api-planner, pr, commit 등 18개 스킬이 팀 전체에서 동일하게 쓰인다 — "팀 배포" 단계의 실사례.

SKILL.md 구조

name — 동명사는 강제 규칙이 아니다

책은 name을 동명사 형태로 쓰라고 하지만, 공식 문서(code.claude.com/docs/skills)엔 그런 규칙이 없다. 공식 예제는 kebab-case일 뿐 형식 강제 없음.

게다가 name은 디스플레이 라벨일 뿐, 실제 커맨드명은 디렉토리 이름에서 온다(플러그인 스킬 제외).

실측: 명사구 ab-test-setup, humanize-korean / 동사형 commit, pr(nova) — 둘 다 정상. 동사형은 오히려 커맨드 성격에 자연스럽다.

분량 — 200줄 이내 (SRP)

양호

pre-chapter-prep 66줄
nova-api-planner 68줄

초과

humanize-korean 257줄 — 오케스트레이터라 길어짐. 리팩터 후보.

지원 파일 — references / scripts / templates

책 권고 — 폴더별 역할

references/: 자주 안 읽는 상세 참고 지식. 본문에서 빼두고 필요할 때만 로드 → 평소 토큰 절약.

scripts/: 반복 로직은 코드로. 클로드가 실행해 결과만 컨텍스트에 남긴다(로직 전문을 안 읽어도 됨).

templates/: 산출물 뼈대. 매번 형식을 새로 만들지 않고 채우기만.

공통 원칙: 도메인별로 분리, 깊이는 1단계까지. 중첩 참조 금지(참조가 또 참조를 부르지 않게).

내 시스템 실측

references/ + evals/: 마케팅 스킬 대부분이 이 구조(seo-audit, copywriting).

scripts/, templates/는 개별 스킬 폴더가 아니라 nova-workflow 플러그인 루트에 존재. 개별 스킬 안에 scripts/를 둔 건 admin-guide-writer 하나뿐.

→ 내 스킬은 아직 references 위주. script/template 활용은 약함 — 도입 여지 있음.

context / agent / background — 컨텍스트 격리

context: fork — 포크된 서브에이전트에서 실행(메인 컨텍스트 격리)
agent — Explore(읽기전용·소형·탐색) / Plan(계획 수립) / general-purpose(기본값·전체 도구)
background — true(기본) 백그라운드 실행 / false 결과 대기
적절

HTML 생성, 대량 검색, 리서치처럼 초점이 좁고 산출물만 필요한 작업 → 격리해 메인 토큰 절약

부적절

메인 대화 맥락을 계속 참조·왕복해야 하는 작업 → 격리하면 컨텍스트가 끊긴다

실측

내 SKILL.md frontmatter 키는 name, description, metadata, disable-model-invocation, argument-hint, allowed-tools뿐 — context/agent/background는 아직 안 씀.

도입 후보: pre-chapter-prep이 이미 3단계 HTML 생성을 "서브에이전트 위임 가능"이라 명시 → 여기에 context: fork + agent: general-purpose를 붙이는 게 첫 적용 지점.

토큰 최적화 5원칙

  1. description 압축 — 100토큰 예산 안에서 발견 확률 극대화
  2. 범용 지식 빼기 — 클로드가 이미 아는 건 빼고 프로젝트 고유·비공개 정보만 (50~70% 절감)
  3. 지원 파일 도메인별 분리, 깊이 1단계까지 — 중첩 참조 금지
  4. 예시는 본문에 1~2개 — 나머지는 EXAMPLES.md로 (예시가 토큰의 20~50%)
  5. 로직은 스크립트로 — 실행 결과만 컨텍스트에 남겨 토큰 급감

적용예시(실측): 마케팅 스킬군이 본문은 얇게 두고 references/로 분리(3원칙), evals/로 예시 격리(4원칙) — 5원칙의 실물. 반대로 humanize-korean 257줄은 본문 비대 → 개선 대상.

정리 + 스스로 던진 질문 → 답

  • 커맨드·스킬은 이제 호출 방식만 다른 같은 포맷 — 화이트박스(직접 제어) vs 블랙박스(자동 선택).
  • 스킬은 로컬 → 프로젝트 → 팀으로 배포 범위를 넓혀간다.
  • SKILL.md는 200줄·SRP + 지원 파일 분리 + context/agent로 컨텍스트 격리.
  • 5원칙으로 스킬 자체의 토큰 무게를 줄인다.

Q1. E2E API 테스트 스킬화 — env 주입

결론: 스킬화 O — 절차는 스킬, 값은 분리. env 값은 SKILL.md에 넣지 않는다.

어디에? settings.json의 env 필드. 스코프 User / Project / Local(settings.local.json), 우선순위 Local > Project > User.

권장: env는 모든 세션 자동 적용 → 1순위. dev/stage 오버라이드·비밀은 gitignore되는 settings.local.json. 필수 env는 CLAUDE.md에 문서화.

스킬 body에서 .env source도 가능하나 env 필드가 더 깔끔.

Q2. 토큰 15% 모니터링 — 쉽게 보는 법

/context: 무엇이 컨텍스트를 쓰는지 시각화. Skills row가 스킬 점유 크기 표시.

statusline: 하단 바에 셸 스크립트로 context bar 상시 표시 가능.

15% = /context Skills row ÷ 전체 윈도우(200K~400K). auto-compaction: 스킬당 첫 5,000토큰 유지·재부착 합산 25,000토큰.
